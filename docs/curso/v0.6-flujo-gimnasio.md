# v0.6 — De una bitácora a un flujo de entrenamiento

## Problema y comportamiento

La aplicación se usa entre series, con una rutina ya preparada. La operación frecuente es registrar peso/repeticiones y continuar; crear o modificar el plan es secundaria. Por eso se abre la última sesión y el ejercicio consultado, mientras la creación de sesiones y el editor quedan apartados del formulario principal.

La rutina de referencia sigue precargada a partir del Excel aportado. Esta entrega no agrega un importador genérico de nuevas planillas: los archivos Excel pueden tener estructuras diferentes. El editor permite crear otras rutinas dentro de la aplicación.

## Contratos del dominio

| Necesidad | Regla | Implementación |
|---|---|---|
| Una sesión por rutina y día | Misma rutinaOrigen.id y fecha: continuar la existente. Otro nombre no crea una sesión distinta. | App busca la existente; crearSesion también rechaza duplicados. |
| Carga inicial útil | Para la primera serie de un ejercicio: primera carga registrada en la sesión anterior de la misma rutina que contenga ese ejercicio. Solo fechas anteriores, identificadores estables. | sugerirPeso en guided.ts. |
| Siguiente serie | Si ya hay series del ejercicio en esta sesión, sugerir su última carga. Nunca crear una serie por sugerir un valor. | sugerirPeso y estado editable del formulario. |
| Menos escritura | Sumas +1,25, +5, +10 y +20; resta −1,25 y puesta en cero. Peso editable y pasos decimales admitidos. | sumarPeso; controles de App. |
| Avance automático | Completar las series previstas avanza al siguiente ejercicio pendiente, aunque las repeticiones reales sean menores al objetivo. Puede elegirse otro ejercicio manualmente. | siguienteEjercicio, ejercicioPendiente. |
| Finalizar | La última serie del último pendiente guarda serie y cierre en una sola escritura del registro. Cierre anticipado requiere confirmar y conserva pendientes. Se puede reabrir. | finalizarSesion, reabrirSesion. |
| Corregir | Una sesión cerrada permite corregir valores; para agregar series debe reabrirse. La hora de registro original se conserva. | corregirSerie y permisos de interfaz separados. |
| Cambiar el plan | Conservar IDs en una edición o cambio de orden; reemplazar un ejercicio por otro requiere una fila nueva. Sesiones existentes no se modifican. | guardarRutina y copia en crearSesion. |

Si un ejercicio fue eliminado y vuelto a crear, obtiene otro ID y no hereda automáticamente la carga anterior. No se comparan nombres para inferir identidad. Si se modifica solo el nombre conservando ID, se interpreta que sigue siendo el mismo ejercicio.

## Del toque al guardado

1. El usuario modifica un borrador de peso/repeticiones. Todavía no es una serie.
2. Registrar valida el borrador y crea una serie con ID, ejercicioId y registradaEn.
3. El dominio produce un nuevo registro inmutable.
4. Se calcula si corresponde avanzar o cerrar. El cierre automático se incorpora al mismo registro candidato que contiene la última serie.
5. useRegistro → storage valida, comprueba vigencia y escribe.
6. Solo con resultado exitoso se actualizan la pantalla, el mensaje y el ejercicio seleccionado.

Si la escritura falla, no se avanza ni se muestra una serie ficticia. No hay un guardado diferido al final: cada serie confirmada se persiste inmediatamente. La aplicación sigue utilizando almacenamiento local; no hay backend ni sincronización.

## Modelo y análisis futuro

Se conserva la clave y el formato v3. Los campos adicionales son opcionales para aceptar registros anteriores:

```ts
type SerieEjercicio = Serie & {
  ejercicioId: string;
  registradaEn?: string; // ISO UTC: momento de registro, no inicio de esfuerzo
};
// Sesion admite finalizadaEn?: string.
// RegistroActual admite rutinas?: RutinaDia[].
```

La fecha de entrenamiento sigue siendo calendario local YYYY-MM-DD. La hora ISO permite mostrar la hora local y preservar el instante. En registros antiguos no se inventan tiempos.

Cada sesión tiene su copia ordenada de ejercicios y objetivos; series guarda la secuencia real de registro. La bitácora usa ese orden incluso si se alternan ejercicios. El resumen agrupa por ejercicio sin alterar esa secuencia. El volumen externo mostrado es Σ(pesoKg × repeticiones); no mide calorías ni contempla peso corporal, desplazamiento, asistencia o diferencias entre máquinas.

La última pantalla se persiste separadamente bajo gim.app.navegacion.v1. No se incluye en el respaldo porque es una preferencia del dispositivo, no un resultado deportivo. Si falta o es inválida, se reconstruye desde las sesiones disponibles. El borrador numérico no enviado no se conserva al recargar.

Los respaldos incluyen rutinas personalizadas, tiempos y cierres. Importación aditiva: mismas identidades y contenido son repetibles, diferencias bloquean todo el archivo. Una sesión entrante con otro ID pero la misma rutina/fecha también se considera conflicto. Los duplicados históricos ya existentes no se borran ni se fusionan automáticamente. Plantillas distintas con el mismo ID requieren resolver la diferencia fuera de una importación automática; esta versión no ofrece sobrescritura forzada.

## Calorías: qué se puede estimar

Tipo de ejercicio, kilos levantados y repeticiones no alcanzan para una estimación fiable por serie. Faltan tiempo de esfuerzo, descansos, peso corporal e intensidad, entre otras variables. Las marcas de registro no equivalen al tiempo activo de contracción.

El Compendio de Actividades Físicas publica valores MET por actividad. Define 1 MET aproximadamente como 1 kcal/kg/hora; ofrece, por ejemplo, 3,5 MET para entrenamiento de resistencia con varios ejercicios y 6 MET para esfuerzo vigoroso. Una aproximación de sesión es kcal ≈ MET × peso corporal en kg × duración en horas. Es una estimación poblacional de gasto bruto, no una medición individual ni un algoritmo preciso por serie.

Fuentes: https://pacompendium.com/ y https://pacompendium.com/wp-content/uploads/2024/01/2024-adult-compendium-tracking-guide_1-2024.pdf?force_download=true

Decisión: no incorporar un contador de calorías a partir de datos insuficientes. Priorizar resultados medidos y volumen; un futuro módulo necesitaría perfil corporal, duración/intensidad y una presentación explícita de su incertidumbre.

## Validación

34 pruebas node:test cubren reglas anteriores, nueva identidad rutina-fecha, carga inicial frente a última carga/futuro/otra rutina, avance con menos repeticiones, navegación, decimales, copias históricas, cierre/reapertura y respaldo de catálogo.

El script app/scripts/verify-guided.cjs verifica la versión de producción en Chrome con perfiles temporales: controles reales, avance, persistencia de última pantalla, edición y orden del plan, cierre, corrección, descarga e importación real, recarga y registro offline y ausencia de desborde en móvil. Se ejecuta con Playwright disponible externamente mediante GIM_PLAYWRIGHT_PATH, sin añadir dependencias al producto.

No inferir aprendizaje del estudiante por la implementación. El próximo análisis técnico puede seguir cómo una misma serie dispara guardado, avance y cierre sin producir confirmaciones parciales.
